# 从ESP32固件到连续速度执行

更新：2026-11-03。本文基于现机`/home/whill/Shaki_ws/esp32_velocity_interface`固件/脚本与仓库内`whill_controller`源码核对，描述从单片机烧录、蓝牙鼠标和App摇杆，到ROS速度接口的完整执行层。当前没有通过本轮文档任务重新烧录或驱动车辆。

## 1. 为什么需要这一层

非EDU轮椅当前使用既有App入口，Jetson不能直接依赖开发版SDK发送左右轮速度。因此执行层把Nav2的(v, omega)目标变成iPad虚拟摇杆位置，再由原厂控制链完成车辆驱动。

```text
Nav2最终速度
  → 时间/坐标校验
  → 标定逆映射得到App目标位置
  → 计算相对鼠标位移并编码
  → USB串口
  → ESP32 BLE HID报告
  → iPad拖动WHILL App摇杆
  → 原厂控制链
  → 轮椅实际运动
```

这里的“底层离散”首先指鼠标报告的方向和位移量化，不是ESP32直接控制一组离散电机转速。

## 2. 单片机与固件构成

现机源码采用ESP32-S3、ESP-IDF v5.3.2，使用USB Serial/JTAG接收命令，NimBLE/ESP HID输出BLE鼠标报告。固件包含：

- USB串口读取任务与命令解析。
- BLE广播、连接、安全/加密及HID报告订阅状态管理。
- 鼠标按钮状态、相对X/Y位移和报告发送。
- 精细帧校验、解析超时与查询诊断。
- 不实际发送HID的台架回放模式。

ESP32不运行定位、地图、路径规划或轮速PID。它执行的是输入设备协议适配。

现机相关原件：

| 文件 | 内容 |
| --- | --- |
| `esp32_velocity_interface/firmware/main/main.c` | 串口任务、方向/按钮命令、HID报告与回放模式 |
| `firmware/main/esp_hid_gap.c` | BLE连接、安全和订阅逻辑，保留Espressif来源声明 |
| `firmware/main/fine_protocol.h` | 精细位移帧解析 |
| `firmware/sdkconfig.defaults` | 构建配置 |
| `firmware/prebuilt/flash_args` | 历史归档镜像的烧录参数/地址 |
| `scripts/set_output_mode.py` | 查询并切换replay/live输出模式 |

固件源码目前仍是现机外部依赖，本次仓库更新只补充说明；不要因有说明就认定固件源码或镜像已全部上传。

## 3. 构建、烧录与部署记录如何理解

现有构建与历史部署使用ESP-IDF v5.3.2。归档`flash_args`记录的特定ESP32-S3镜像布局为：

| 内容 | 历史地址 |
| --- | --- |
| bootloader.bin | `0x0` |
| partition-table.bin | `0x8000` |
| ble2wchair_mouse.bin | `0x10000` |

该文件同时记录`dout / 80m / 32MB`。这是这套归档镜像的参数，不应当作任何ESP32板子的通用烧录模板。需要换板或重烧时，应核对目标芯片/flash配置、镜像SHA与现有固件备份，再按匹配工具操作；文档更新不执行这些操作。

历史材料包含多个阶段：先从草稿重建固件并做无运动回放，之后记录了2026-10-30备份与部署。旧README仍同时保留“not flashed”“bench only”和后续部署更新，不能只取某个旧标题判断当前状态。`BUILD_VERIFICATION.json`主要证明对应构建/台架产物，不能单独证明今天板上运行的每一字节或当前实车已经通过所有动作。

维护时应分别保存：源码版本、构建环境、镜像SHA、备份/烧录记录、板端能力读回、HID实际发送记录和里程计运动证据。它们证明的环节不同。

## 4. USB与BLE不是同一条连接

`/dev/ble2wchair`是Jetson上的USB串口设备别名，并不是Linux蓝牙网卡。上位机串口配置使用115200，原生USB Serial/JTAG的传输还取决于USB驱动与缓冲，不能直接按传统UART字节时间估算整条系统延迟。

`serial_connection.py`识别ESP32-S3原生USB，使用独占串口，并处理DTR/RTS和Linux HUPCL，避免普通打开/关闭串口意外复位USB控制器。

ESP32随后作为BLE HID鼠标连接iPad。固件readiness依赖连接、安全/加密及报告订阅等条件，MTU协商或单独的连接事件不被直接等同于已可发送。连接epoch改变时会清理相关帧/按钮状态。App到轮椅仍走原厂链路，该链路细节不是本工程HID代码的一部分。

现场接通时应区分两件配对/连接事务：iPad与ESP32的HID连接，以及WHILL App与轮椅的原厂连接。前一项成功不证明后一项正常。之后保持屏幕方向、App布局和指针设置与标定一致，完成指针归位/摇杆中心核对，再由现有启动入口设置live模式、现场使能并接受上层命令。本轮仅描述该流程，不重新配对或操作设备。

## 5. 原有离散指令

以下以固件当前解析逻辑为准：

| 串口命令 | HID含义 |
| --- | --- |
| `w / a / s / d` | 相对Y-/X-/Y+/X+，每步25 HID单位 |
| `q / e / z / c` | 对角相对位移，每轴18 HID单位 |
| `[` | 鼠标左键按下，用于拖住摇杆 |
| `]` | 松开按钮；也可打断当前精细帧 |
| 回车 | 条件满足时发送点击 |
| `h / j` | 释放后按固定序列向屏幕边界移动，供归位流程使用 |
| `?` | 查询BLE、精细协议及回放/发送状态 |
| `{ / }` | 进入台架回放 / 离开台架回放 |

上位机键名与固件命令不是一一同名：例如上位机的组合方向会先经过`COMMANDS`字典转换。文档或测试应明确讨论的是按键、串口字节还是HID报告。

旧协议不是“w直接等于0.5m/s”。w改变指针位置，App摇杆的新位置才间接决定车辆速度。粗步长在半径只有若干旧步的摇杆范围内会造成明显量化。

## 6. 精细相对位移协议

精细帧形式：

```text
~XXYYCC\n
CC = XX XOR YY XOR 0xA5
```

X/Y采用8位有符号相对位移表示，协议支持-127到127。帧只改变鼠标位移，不更改按钮保持状态。当前上位机编码器为保留原有操作顺序，先发X再发Y，整段仍按25单位拆分，再添加较小余量；不是把所有移动合成一个大跳。

格式错误、校验错误等帧不作为正常移动执行；解析器超过100ms无新字节会清除半帧。**这个100ms是帧解析超时，不是轮椅速度流看门狗，也不等于100ms内车辆一定停稳。**

主机旧坐标单位仍代表25 HID单位。精细模式可用1/25个旧单位表示一个HID单位；一HID单位也不保证等于屏幕上的一个像素，iPad指针增益/加速度仍可能影响实际位置。

当前`main.c`普通报告发送后名义等待10ms，归位报告另有等待。历史说明中有20ms描述，维护时以对应固件源码和实测为准。20Hz上层速度更新不意味着每次鼠标重定位都能在20ms内完成；多报告序列、USB队列和BLE调度会共同影响响应。

## 7. 从App坐标标定到稳态速度模型

两种标定职责不同：

1. **界面几何标定**：确定屏幕边界归位、摇杆中心及方向锚点。`ipad_calibration_20261009.json`保存九个参考点的操作序列，依赖特定App布局与指针设置。
2. **速度标定**：在已知App输入下记录后轴Odin速度，拟合摇杆输入与(v, omega)关系。当前`velocity_mapping.py`使用2026-10-30连续模型。

归位与移动过程中，上位机维护的是推算的指针坐标；当前不是通过屏幕视觉实时读取指针位置的闭环。App布局、屏幕方向或指针设置改变后，应重新核界面坐标，不能只沿用旧目标位置。

令x为归一化向右输入、y为归一化向前输入，先把超出单位圆的输入沿径向缩放。当前模型：

```text
v = 0.536622219601921 * y        (y >= 0)
v = 0.40367094263942477 * y      (y < 0)
w = -0.8108854254075847 * x
```

ROS中正w是左转，因此向右输入对应负w；屏幕Y向下，向前又对应屏幕Y减少。逆映射先根据目标v/w计算x/y，再转换为摇杆中心附近坐标；超出可达范围时沿输入射线缩放。

最大前速和最大角速不能同时达到。可达集合是前/后纵轴不同的半椭圆，而不是独立将v、w各自夹到最大值的矩形。

| 轴 | 旧一坐标步的模型变化 | 精细一HID单位的名义模型变化 |
| --- | --- | --- |
| 前进 | 约0.06708m/s | 约0.002683m/s |
| 后退 | 约0.05046m/s | 约0.002018m/s |
| 转向 | 约0.10136rad/s | 约0.004054rad/s |

这是坐标量化在模型中的对应关系，不是实车独立测得的最小速度精度，更不能据此宣称实体跟踪提高25倍。

现机历史标定报告使用4个完整bag、33段稳定区间，留一bag验证的线/角速度RMSE约0.02263m/s、0.01123rad/s。数据来自同一录制会话和筛选规则，不能当作不同地面、载荷、App档位下的通用精度保证；精细HID的独立低速性能还需要对应真实数据确认。

## 8. ROS速度如何落到App拖动

1. `cmd_vel_adapter`将Nav2最终Twist加上当前时间与`base_link`，发布`/whill/controller/navigation`；若输入本来带时间戳则保留源信息，不重播旧速度。
2. 执行节点校验frame、有效期、有限数值及差速轴约定。当前非零速度流按约200ms的时效处理。
3. 连续映射模式调用`map_velocity`，记录期望速度、量化后的HID目标点和模型可实现速度。
4. 开始运动时复用回中心、左键按下、移动至目标的拖动流程；持续输入更新目标位置，不是每周期松开再按下。
5. 停止或暂停时释放按钮，并清理缓存目标；具体释放与归位由既有执行流程完成。

`native_nav2_mode=true`、`navigation_continuous_mapping=true`是当前原生导航模式；精细HID由launch启用并核能力。执行节点本身的参数默认值与最终launch传参不同，不能只看类里的默认false就判断运行没开。

## 9. 动态平滑与反馈边界

当前底层映射是标定前馈，没有在ESP32或`cmd_vel_adapter`里额外实现线/角速度PID。Odin反馈进入Nav2的位姿/控制链；它也可用于记录期望、映射与真实响应的差异。

Nav2速度平滑配置为线加减速度±0.33m/s²、角加减速度±0.8rad/s²。这是导航的命令约束，不是电机铭牌上限，也不代表实际执行精确具有相同斜率。`measured_dynamics.yaml`记录历史里程计推算的事件平均加减速度；`dynamics_reference.yaml`是旧参考，不能反过来覆盖当前导航配置。

需要同时区分：路径几何平滑、命令速度平滑、命令加速度约束、HID量化、实际速度跟踪和最终停车误差。上层有平滑器不等于整条链天然没有延迟、跳变或冲过终点；当前也没有宣称jerk连续或强制梯形速度时间参数化。

## 10. 模式、授权与停止

固件源码开机进入台架回放模式；该模式记录HID_DRY而不实际发送HID。导航启动脚本会通过`set_output_mode.py live`切换，再启动底盘节点。**live模式与ARM不是同一状态**：前者允许固件发送，后者允许上位机执行输入。

当前Nav2使用保持式ARM。出现输入超时、串口/BLE异常等情况时，可暂停输出、释放拖动并按条件取消目标，保持授权状态；进程重启仍默认未使能。短暂速度超时有恢复窗口，较长故障后需要符合新鲜零速或新目标等条件。不能将“ARM绿色”直接理解为“此刻一定允许运动”。

| 观测/状态 | 能说明什么 |
| --- | --- |
| 串口已打开 | Jetson能访问USB设备，不证明iPad已连接 |
| BLE readiness | HID链满足固件条件，不证明App摇杆坐标正确 |
| HID发送/通知计数 | 报告进入对应发送环节，不是电机速度反馈 |
| ARM / 输出暂停原因 | 上位机授权与当前阻断状态 |
| Odin真实速度 | 实体后轴运动的观测，仍需考虑标定和时间语义 |

上位机失联处理、固件帧超时和车辆物理制动是三件事。不能用其中一项代替其余两项的验证。
